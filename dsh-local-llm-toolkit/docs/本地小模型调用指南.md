## 2. 硬性纪律（机制，跨版本存活）

### 2.1 ⛔ 1234 端口不会自启

重启后 LM Studio 在跑，但 1234 **拒连**。开工第一步永远是：
```powershell
& "$env:USERPROFILE\.lmstudio\bin\lms.exe" server start
# 或界面：Developer -> Status 开关
```

### 2.2 ⛔ 8GB 显存一次只站得下一个 7B

换模型要 **20–40 秒**加载。**不要设计"两个模型轮流上"的流程** —— 每次切换都是纯浪费。

### 2.3 ⛔ 绝不让第二个模型被 JIT 偷偷加载（最危险的坑）

**实测事故**：质检环节用另一个模型，LM Studio 的 JIT 把它也拉进显存，**两个 7B 同时驻留 → 显存只剩 150 MiB**，逼近 OOM。

**正解：两阶段流程**
```
第一阶段：翻完全部内容（只用翻译模型）
第二阶段：卸载翻译模型 -> 加载质检模型 -> 统一复核
```
**任何时候都不要在同一个循环里交替使用两个模型。**

### 2.4 ⛔ `lms` 的输出在管道里是空的

`lms server status` / `lms ps` 被重定向或管道捕获时**什么都不输出**。**不能靠它的 stdout 判断状态**，一律查 `GET /api/v0/models` 的 `state` 字段（`loaded` / `not-loaded`）。

### 2.5 ⛔ 单块别超 1800 字（否则它在"总结"而不是"翻译"）

**实测数据**（同一本书，按块大小分组看"译文字符/源字符"比值）：

| 源字符区间 | 平均比值 |
|---|---|
| 1200–2000 | 0.341 |
| 2000–3000 | 0.317 |
| 3000–4500 | 0.302 |
| 4500–7000 | **0.270** |
| 7000+ | **0.201** |

块大到一定程度，模型会**压缩概括**。铁证：块 205（8211 字）的译文结尾冒出原文根本没有的一句"总之，终身教职申请是一个复杂且重要的过程"。

**正解**：送模型前按**句子边界**切成 ≤1800 字的子块（分块器实现见 `E:\0001bendiAI\文档流水线\pipeline.py` 的 `split_long()`）。修完后所有尺寸区间的比值都收敛到 0.30–0.34。

### 2.6 ⛔ 它当裁判不可信，只能当筛子

**实测**：让 `qwen2.5-7b-instruct` 复核 63 块译文，19 条报警里 **7 条是误报**；它会一边判"失败"一边在理由里写"翻译完整准确"。

**正解**：本地模型只做**机械检查**（段落数、长度比、拒答词、重复段、未译残留）；**真假判定必须由我回原文核对**。19 条报警逐条核完，真错只有 4 条（1.3%）。

### 2.7 ⛔ 它是纯函数

无记忆、不能碰文件、不能上网、不能调工具。每次调用都要把全部上下文重新递一遍；8192 上下文用完即弃。

## 3. 标准五步

```
① 排班  GET  /api/v0/models                    看谁在岗；不对就先 unload 再 load
② 分块  <=1800 字，按句子边界切
③ 派活  POST /v1/chat/completions              system 岗位提示词 + temperature + max_tokens
④ 自检  机械检查（零成本）+ 抽样模型复核（只能当筛子）
⑤ 收工  lms unload
```

**③ 的真实形态**（`run_code` 里，可 `Promise.all` 并发）：
```ts
const r = await fetch('http://127.0.0.1:1234/v1/chat/completions', {
  method: 'POST', headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify({
    model: 'hunyuan-mt-7b', temperature: 0.3, max_tokens: 2048,
    messages: [{ role: 'system', content: '你是专业翻译引擎，只输出译文，不要解释' },
               { role: 'user',   content: '要翻译的段落' }] })
})
```
**并发实测**：三个独立请求串行 3.4s → `Promise.all` 并行 1.4s，**加速 2.43×**（模型 `--parallel 1` 时仍有效，因为是不同请求排队）。

**加载参数的坑**：`Parallel` 默认是 **4**，等于把 KV cache 复制 4 份。**单用户务必改成 1** —— 实测显存从"只剩 150 MiB"变成"剩 1564 MiB"，速度还从 19 tok/s 涨到 **39 tok/s**。
```powershell
lms load hunyuan-mt-7b --gpu max -c 8192 --parallel 1 -y
```

## 4. 什么活该外包，什么绝对不能

### ✅ 该给她们 —— 三个条件缺一不可

1. 输出能**机械核对**（我能对照原文判对错，不用"信"她）
2. 输入能**切成独立小块**
3. 错一块**不影响整体**

→ 翻译、摘要、信息抽取、格式转换、大批量初筛打标。

### ❌ 不该给她们

| 类型 | 实测反例 |
|---|---|
| 要跨块一致的 | 术语统一翻车：`Dean and the Faculty` 译成"校长与教务处"（应为"院长与教师队伍"） |
| 当裁判 | 19 条报警 7 条误报 |
| 要多步推理 / 调工具 / 记上下文 | 纯函数，做不到 |
| 靠"看着别扭就改"来纠错 | 曾误判 `yoga`（原文真写了 yoga）和 `[DAVH]`（是文献引用键）**都是对的** |

**纠错前必须回原文核对**，否则会把对的改错。

## 7. 成本提醒：别拿"省钱"当外包的理由

**实测账**（286 页英文书）：本地全译电费约 **¥0.07**；云端 DeepSeek-V4.1-Flash 直译 **¥0.69（闲时）**。

**本地部署买的是隐私、可重复、不受限流，不是省钱。**

**而且**：本地干粗活 + 云端**全量**精修 = **比直译更贵**（输出要写两遍）。真正划算的姿势是"**本地干完 98.7%，云端只碰出问题的那 1.3%**"。

**最贵的是验证**：她们翻 286 页 = 0 元；我花在"发现压缩 bug + 核对 19 个报警 + 修提取器"上的精力 = 整个会话的大头。

> 判断要不要外包，别问"小模型能不能做"，要问：**我能不能便宜地验证她做对了？**
> 能机械验证 → 放心外包，还能并发铺开；不能验证 → 外包出去的每一份产出都会变成后面要还的债。
