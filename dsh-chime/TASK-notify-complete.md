## 1. 问题：两个渠道都只做了「发出去」，没做「发出去之后」

用户的原话是「这两个好像你没做完整」。核对后确实如此：

### 1.1 标签页标题闪烁（现状 `lib/client.js` 的 `flashTitle`）

```js
let titleTimer = 0
let savedTitle = ''
function flashTitle(kind) {
  if (!savedTitle) savedTitle = document.title
  if (titleTimer) window.clearTimeout(titleTimer)
  document.title = (kind === 'complete' ? '✅ ' : '🔔 ') + savedTitle
  titleTimer = window.setTimeout(() => { document.title = savedTitle; titleTimer = 0 }, 6000)
}
```

| 缺陷 | 用户会看到什么 |
|---|---|
| 不看页面是否可见 | **人正盯着页面**，标题也在那儿闪 6 秒——纯噪音 |
| 只在定时器到点时恢复 | **切回页面的那一刻不会安静**，还得等剩下的几秒 |
| `savedTitle` 只在首次记录 | 若首次记录发生在标题**已带图标**的时刻（例如上一次闪烁中插件重载），图标会被**永久写进**标题 |
| 只换 emoji | 完全看不出是「哪一条」在闪，两条通知连闪两轮也分不清 |

### 1.2 桌面通知（现状）

```js
if (settings.notifyDesktop && typeof window.Notification === 'function') {
  try {
    if (window.Notification.permission === 'granted') {
      new window.Notification(kind === 'complete' ? '活干完了' : '需要你协助', { body: detail || '' })
    }
  } catch (error) { /* 通知失败无所谓 */ }
}
```

| 缺陷 | 用户会看到什么 |
|---|---|
| 点击通知**没有任何行为** | 想点通知跳回页面 → 点了没反应，还得手动找窗口 |
| 权限非 `granted` 就**静默不弹** | 开关开着、铃响了、弹窗没了——用户以为插件坏了 |
| 权限**请求结果被忽略** | 用户正在弹窗里犹豫时到来的通知被直接丢弃；拒绝后开关仍显示「开」 |
| 没有 `tag` | 同一件事连弹多条，系统托盘里**堆一排** |
| 没有 `requireInteraction` / 生命周期管理 | 多条通知同时挂着，分不清哪条最新 |
| 标题写死、正文信息少 | 不知道是哪个会话、什么事 |

## 2. 目标（可验收）

### 2.1 标题闪烁

1. **只在页面不可见时闪**：`document.hidden === true` 才动标题；页面可见时完全不碰标题。
2. **切回页面立刻恢复**：`visibilitychange` 且可见时立即还原（不等定时器）。
3. **图标绝不累积**：连续多次闪烁、或插件重载后再闪，标题里都只有**一个**图标；`savedTitle` 必须能识别并剥离已有前缀。
4. **闪烁期间带信息**：标题前缀里体现「有几条待看」（例如 `🔔(2)`），让用户扫一眼就知道积了几条。
5. 恢复定时器仍保留（防止一直闪），时长可沿用 6 s。

### 2.2 桌面通知

1. **点击 = 回到页面**：点击通知 → `window.focus()`；并关闭该通知。若宿主能提供「会话说」的入口，优先跳到那条会话（做不到就只聚焦窗口，别硬造）。
2. **权限状态可见**：设置页「桌面通知」那一行要显示当前状态：`未请求` / `已授予` / `已拒绝` / `此浏览器不支持`。开着开关但状态是「已拒绝」时，必须明确提示用户去浏览器设置里放开。
3. **权限未定时不静默丢**：若 `permission === 'default'`，发通知前先 `requestPermission()`，拿到结果再决定发不发；**结果要回写到设置页状态**。
4. **合并重复**：给通知设 `tag`（同一类别同一 tag），保证系统里最多留一条同 tag；新一轮通知标题标注「第 N 条」。
5. **失败要说出来**：构造 `new Notification()` 抛异常时，不能只 `console` 吞掉——在「最近的通知」记录里写一条「桌面通知失败：<原因>」。

## A2. 追加要求（必做）：权限请求加「单飞」，别并发弹

**问题（真实存在，非推测）**：装配处是

```js
requestPermission: () => window.Notification.requestPermission(),
```

权限仍为 `default` 时，**短时间内连续到达多条通知**会让每个 `notify()` 各自调一次 `requestPermission()`。后果：

1. 可能连续弹多个授权询问（浏览器通常合并同源请求，所以视觉上多为一个，**但这不是保证**）；
2. 更实际的问题：后到的通知会立刻走到 `permission !== 'granted'` 分支，各记一条
   `桌面通知未弹出：系统权限是「default」…`
   —— 用户「最近的通知」里会冒出**两三条误导性的失败记录**，而他只是还没来得及点「允许」。

**要求**：

1. 权限请求实现**单飞（single-flight）**：进行中的请求复用同一个 Promise，完成后清空；后续并发调用等同一个结果，**不得重复调用 `requestPermission()`**。
2. 等待期间到达的通知：拿到最终权限后按结果处理（授予就补弹，拒绝就只记**一条**提示，不要每条都记）。
3. 保持既有语义：`default` 不静默丢、结果回写设置页状态（`onPermission`）、`denied` 时那条操作指引不变。

> **A2 完成记录（2026-10-11）**：单飞实现在 `createDesktopNotifier` 内部（`requestPermissionOnce()`：inflight Promise 复用、settle 后清空、`onPermission` 只回写一次）；`deniedHinted` 标志让拒绝提示一个请求周期只记一条（授予成功或新请求开始时复位）。用例 17/18/19 全部落地，`npm test` **84/84 全绿**（81 → 84）。变异验证：去掉单飞恢复直调 → 用例 17 变红（12/19 因结果回写与去重同处而联动变红，符合预期），已还原复绿。
